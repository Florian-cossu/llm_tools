# Data store

A local SQLite database under `data/`, applied by a migration runner that reads
plaintext `.sql` files. It exists to hold the **per-tool permission state** that
[ADR-0007](../../03-decisions/ADR-0007-writes-behind-declared-capability.md#the-permission-layer)
describes.

> [!note] Read and edited, and now the only registration gate
> The [control panel](control-panel.md) reads and edits `state` through this
> store, and `tools/github/src/index.ts` reads it back via `data/access.ts`'s
> `isToolAllowed` — the **only** filter `TOOL_REGISTRATIONS` goes through
> ([ADR-0008](../../03-decisions/ADR-0008-permission-table-gates-registration.md),
> [ADR-0009](../../03-decisions/ADR-0009-permission-table-is-the-only-write-gate.md)).
> There is no separate `GITHUB_ALLOW_WRITES` anymore; it was removed once this
> table's default-deny made it redundant. A row flipped to `deny` (or left at
> its seeded default) keeps that tool out of the model's list — after a
> **server restart**, since the table is still read once at startup. `ask` is
> stored and constrained but has no effect distinct from `deny` yet, and
> nothing audits who changed a row. See
> [current plan](../../07-plans/current.md).

## Layout

```
data/
├── migrate.ts              the runner
├── access.ts               the read API — Bun only, see "Reading it" below
├── harness.db              generated, gitignored
└── migrations/
    ├── 0001_init_servers_table.sql
    ├── 0002_init_github_profiles_table.sql
    ├── 0003_init_permissions_table.sql
    ├── 0004_add_github_tools_permissions.sql
    └── 0005_add_icon_columns_for_servers.sql
```

`harness.db` is **not committed** — it is local state, regenerated by running
the migrations. The `-wal` and `-shm` siblings are gitignored too: the runner
checkpoints and truncates them on a clean exit, but a crashed run leaves them
behind.

## Running it

```bash
bun run migrate       # applies every migration not yet recorded
```

Safe to run repeatedly. A second run applies nothing.

Both paths inside the runner are resolved against `import.meta.url`, not the
working directory, so it behaves identically from anywhere in the tree.

## How the runner works

Six steps, in [`data/migrate.ts`](../../../data/migrate.ts):

1. Open `harness.db`, creating it if absent, and set `journal_mode = WAL`.
2. Create the `meta` bookkeeping table if it does not exist.
3. Read `meta` for the filenames already applied.
4. List `migrations/*.sql`, sorted by filename, and skip the applied ones.
5. Inside a transaction, run each remaining file and insert its filename into
   `meta` with an ISO timestamp.
6. Checkpoint the WAL, then close.

### `meta`

The runner's own bookkeeping. One row per applied migration:

| Column | Purpose |
| --- | --- |
| `filename` | Primary key. The bare filename, not a path — an absolute path would be machine-specific |
| `applied_at` | ISO-8601 timestamp |

Nothing but the runner reads or writes this table.

## Adding a migration

1. Create `data/migrations/NNNN_short_name.sql`, taking the next number.
2. Write plain SQL. Several statements in one file are fine; separate them with
   semicolons.
3. Run `bun run migrate`.

Two rules make the rest work:

- **Zero-pad the number.** Ordering is a lexicographic sort of the filenames,
  so `10_` sorts before `2_` unless the widths match.
- **Never edit a migration that has been applied.** It is recorded in `meta`
  and will not run again, so the edit reaches no database that already ran it.
  Correct a mistake by adding the next migration. Deleting `harness.db` hides
  this during early local work — that stops being an option the moment anyone
  else has a copy.

## Schema

Three tables, one per migration plus a seed. `github_mcp`, the single
per-tool table this note used to describe, is gone — split into `servers`
(so a second MCP server has somewhere to attach its own rows) and
`permissions` (the per-tool decision, now scoped by `server_id`), plus a new
`github_profiles` table that has nothing to do with permissions at all.

### `servers`

[`0001_init_servers_table.sql`](../../../data/migrations/0001_init_servers_table.sql)
creates it and seeds the one row that exists today;
[`0005_add_icon_columns_for_servers.sql`](../../../data/migrations/0005_add_icon_columns_for_servers.sql)
adds the icon columns and backfills them for that row:

| Column | Purpose |
| --- | --- |
| `id` | Primary key |
| `slug` | Unique, e.g. `'github'` — what code looks servers up by |
| `server_name` | Display name, e.g. `'GitHub'` |
| `description` | One line, shown by the control panel |
| `icon_name` | Nullable. A lucide-react icon name or a local SVG's basename, depending on `icon_source` |
| `icon_source` | Nullable. `CHECK (icon_source IN ('lucide', 'local'))`. `NULL` (the default for every server but `github`) falls back to a generic sidebar icon rather than failing the check — SQLite's `CHECK` only rejects a row when the expression evaluates false, and it evaluates to unknown, not false, when either column is `NULL` |

Both readers below expose `icon_name`/`icon_source` as optional — `undefined`
when a server has no icon set — since the columns are nullable and only
`github` is seeded.
[`control_panel/lib/servers.ts`](../../../control_panel/lib/servers.ts) is the
control panel's reader: `listServers()` for nav, `findServerBySlug(slug)`
everywhere a per-server lib (like `github_profiles.tsx` below) needs its own
`id` to scope a write by.

### `github_profiles`

[`0002_init_github_profiles_table.sql`](../../../data/migrations/0002_init_github_profiles_table.sql).
A named preset of "which owner/repo does this server talk to", not a
permission row — nothing here is `allow`/`deny`/`ask`.

| Column | Purpose |
| --- | --- |
| `id` | Primary key |
| `server_id` | FK to `servers.id` |
| `profile_name` | Unique |
| `repository_owner` / `repository_name` | The default owner/repo the profile points at |
| `is_active` | `BOOLEAN DEFAULT 0`. At most one row is ever `1` per server |

> [!note] The single-active invariant is enforced in the write, not the schema
> There is no `UNIQUE` or partial index stopping two rows from both being `1`
> — [`setGithubProfileActive`](../../../control_panel/app/servers/github/lib/github_profiles.tsx)
> keeps that true by writing `is_active = (id = ?)` across every row for the
> server in one statement when turning a profile on, rather than clearing the
> old one and setting the new one as two separate writes. See
> [control panel](control-panel.md#github-profiles).

### `permissions`

[`0003_init_permissions_table.sql`](../../../data/migrations/0003_init_permissions_table.sql)
creates the table; [`0004_add_github_tools_permissions.sql`](../../../data/migrations/0004_add_github_tools_permissions.sql)
seeds its ten rows for the github server. This is `github_mcp` under a new
name and a new key — one row per tool, but scoped to a server instead of
assuming there is only ever one:

| Column | Purpose |
| --- | --- |
| `id` | Primary key |
| `server_id` | FK to `servers.id` — replaces the old free-text `server_name` column |
| `slug` | The public tool name, matching `TOOL_NAME`. Unique per `server_id`, not globally |
| `tool_effect` | What the tool does upstream: `read`, `write` or `destructive` |
| `description` | One line, for the control panel to show without importing tool code |
| `default_state` | The seeded decision. What `state` resets back to |
| `state` | The live, editable decision: `allow`, `deny` or `ask`. Defaults to `deny` |

The ten rows `0004` seeds match `TOOL_REGISTRATIONS` in
[`toolbox/index.ts`](../../../tools/github/src/toolbox/index.ts): the six reads
seeded `allow`, the four mutations seeded `deny`. No row is seeded `ask` —
nothing implements asking yet.

`0004`'s `tool_effect` for `delete_github_label` (`destructive`) now matches the
tool's own `TOOL_EFFECT` export — they used to disagree, which was a known
defect while only `TOOL_EFFECT` gated anything. `tool_effect` is still
hand-maintained by whoever writes the migration, not generated from
`TOOL_EFFECT`, so the two columns *can* drift again; nothing enforces they
agree. What changed is that `state` now matters too:
`tools/github/src/index.ts` reads it via `data/access.ts`'s `isToolAllowed`
as a second registration filter, alongside the `TOOL_EFFECT` gate
([ADR-0008](../../03-decisions/ADR-0008-permission-table-gates-registration.md)) —
so a tool must pass both to register, and `tool_effect` drifting from
`TOOL_EFFECT` is now a documentation problem rather than a gate one, since the
gate never reads this column.

Three constraints carry rules rather than leaving them to convention:

- `DEFAULT 'deny'` on `default_state` encodes ADR-0007's deny-by-default rule
  at the column, so a row inserted without a decision is inert rather than
  permissive.
- `CHECK (state IN ('allow', 'deny', 'ask'))` and the same check on
  `default_state` make the vocabulary a closed set. `'alow'`, `'ALLOW'` and
  `''` are all rejected at write time — the database's version of the argument
  [T8](../../04-contracts/tool-contract.md#input-schema) makes for `z.enum`
  over a bare string, and the one ADR-0007 makes when it rejects free-form
  effect classes.
- `CHECK (tool_effect IN ('read', 'write', 'destructive'))` closes the same
  vocabulary over the effect class.

> [!note] A new tool needs a migration
> Nothing generates these rows from `TOOL_REGISTRATIONS`. Adding a tool without
> adding a row leaves it unlisted — which, once the permission layer exists and
> denies by default, means inert. Neither does anything reconcile a stored
> `tool_effect` against the code's `TOOL_EFFECT`, so a migration that gets
> the class wrong is wrong until the next migration corrects it. See
> [tool contract](../../04-contracts/tool-contract.md).

## Reading and writing it

`data/access.ts` matches the current schema and is what
`tools/github/src/index.ts` imports for `isToolAllowed` at registration —
`listServers()` / `findServerBySlug()` against `servers`, and
`listToolPermissions()` / `findToolPermission()` / `isToolAllowed()` against
`permissions`. It is Bun-only (`bun:sqlite`), so nothing under `control_panel/`
(Node) can import it.

[`control_panel/lib/db.ts`](../../../control_panel/lib/db.ts) is the Node
mirror of `data/access.ts`'s `permissions` reads — `bun:sqlite` /
`node:sqlite` are each available only in their own runtime, so it cannot just
import `data/access.ts`. It opens `harness.db` **read-only** for
`listAllPermissions()` / `listPermissions(serverId)` /
`findToolPermission(slug, serverId)`, and a **second, read-write** connection
for `updateToolState` / `resetToolState`, so the read path every page uses
stays on the read-only connection.
[`control_panel/lib/servers.ts`](../../../control_panel/lib/servers.ts) is the
same kind of mirror for `data/access.ts`'s `servers` reads, and
[`control_panel/app/servers/github/lib/github_profiles.tsx`](../../../control_panel/app/servers/github/lib/github_profiles.tsx)
follows the same read-only/read-write split for `github_profiles`, which has
no Bun-side reader at all yet. See [control panel](control-panel.md), which is
what calls the writers.

> [!note] Nothing is generated from anything else here
> A schema change to `permissions`, `servers` or `github_profiles` means
> editing the `SELECT` columns and the row type in whichever of `data/access.ts`
> and the `control_panel/lib/` files touch that table by hand. Nothing checks
> that they still agree — `0005_add_icon_columns_for_servers.sql` needed the
> same two columns added in both `data/models/ServerDescriptor.ts` (Bun) and
> `control_panel/lib/servers.ts` (Node).

## Why SQLite

ADR-0007 named it: local to the machine, user-editable without touching code,
and consultable before execution so a decision changes behaviour without a
server restart — unlike registration, which is frozen at startup
([execution lifecycle](execution-lifecycle.md)).

Plaintext `.sql` migrations rather than a schema defined in TypeScript, because
the schema is then versioned, reviewable in a diff, and applied by something
small enough to read in one sitting.
